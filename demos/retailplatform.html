Retail Analytics Platform

Transaction simulator → validated API → normalized database → live KPI dashboard. Start the stream and watch each transaction get checked, stored and counted, including the ones that get rejected.

About this demo: a lightweight in-browser re-creation of the pipeline. The real project runs a Python simulator, a FastAPI + Pydantic + asyncpg backend, PostgreSQL 15 in Docker and a Streamlit dashboard. Here, JavaScript functions replicate the same validation rules, the 4-table schema and the KPI queries (ingest.py, kpi.py, sales.py) in memory. Nothing is sent to a server and the data is synthetic. The repo's simulator sends one transaction every 30 seconds; the speed slider here is just for demonstration. The ~15% “bad payloads” are injected by this demo to show rejection paths (toggle them off if you like), they are not real failure rates.

In-memory database normalized schema

Rules replicated from the repo

  • Pydantic model (TransactionPayload): customer_id must be a UUID, product_ids a list of UUIDs, quantities a non-empty list of ints; payment_method defaults to credit_card and status to completed. Failures return 422.
  • API check: len(product_ids) != len(quantities) returns 400.
  • Database (schema from force_create_tables.py): customer FK, status in completed / cancelled / refunded, quantity > 0. A violation rolls the whole transaction back (500). Unknown product IDs are skipped, as in the endpoint; a transaction whose items were all skipped is stored with no line items and so doesn't count in the KPIs.
  • Not replicated: asyncpg pooling, retries with backoff, Streamlit page layout, auto-refresh and persistence. Refreshing this page resets the store.
